# BLE 配置分包确认协议

> 本文记录旧版协议，仅供兼容参考。当前 APP 已改为普通 JSON 行收发，不再使用逐包业务确认；以 [BLE JSON 收发说明](BLE_JSON收发说明.md) 为准。以下“必须等待 ACK”等要求只针对旧版 APP。

适用于 Arduino ESP32-S3 固件和 UniApp 手机端。Wi-Fi/MQTT 配置 JSON 字段和 BLE UUID 不变，只改变分包传输方式。**手机端和开发板固件必须一起更新。**

## 目的

当前 Arduino-ESP32 3.3.3 的 NimBLE 实现会延后执行 `onWrite()`，连续写入时，回调读取的特征值可能已被下一包覆盖。因此手机不能只等待原生写入成功，必须等待开发板实际复制载荷后的应用层确认。不自动降级为无确认连发。

## 物理写入格式

```text
@iiiiiiiisss:payload
```

`iiiiiiii` 是 JSON 内相同的 8 位小写十六进制请求 ID；`sss` 是从 `000` 开始的三位小写十六进制包序号；`payload` 最多 7 个原始 UTF-8 字节，可以在中文字符的字节中间分包。13 字节头加最多 7 字节载荷，每次物理写入不超过 20 字节。

完整 JSON 仍以真实换行字节 `0A` 结束，总长度最多 1024 字节。首包示例：

```text
@a1b2c3d4000:{"id":"
```

下一包序号为 `001`，十进制 10 对应 `00a`；请求 ID 不变。

## 应用层收包确认

开发板回调完成载荷复制和顺序校验后，排队发送：

```json
{"id":"a1b2c3d4","event":"chunk_ack","seq":0}
```

`seq` 是 JSON 数字。回复仍以换行结束，经最多 20 字节的 notify 分片发送，手机收齐一行再解析。手机只接受本次请求 ID 和当前序号均匹配的确认；重复确认、其他 ID、其他序号都不能释放下一包。ACK 不会被显示为配网成功。

固件拒绝乱序包，紧邻重复包只重发 ACK、不重复拼接，重复最终包不重复派发配置。新请求的 `000` 包重置未完成的拼包状态。完整 JSON 校验成功后，固件先排队最终 ACK，再把请求交给主循环。

配置完成仍以 `wifi_connected` / `wifi_failed` 或 `mqtt_connected` / `mqtt_failed` 为准，不把收到所有字节当作联网成功。明确的最终成功回包可以作为最后一包已处理的证据，避免仅丢失最终 ACK 时覆盖真实成功结果。

## 超时与升级

- 每包确认等待 6 秒，为当前主循环的 MQTT TCP/CONNACK 最长约 4 秒等待留出余量；整条请求等待 45 秒。
- 超时、写入失败、协议错误或断连时停止发送并清理等待状态，不盲目重发。
- 无 ACK 不代表 Wi-Fi 密码错误；先确认双方版本已更新，再重连、重新提交。
- `invalid_chunk`：包头、长度或序号错误；`invalid_json`：拼接后的 JSON 解析错误。
- 固件保留旧版直接发送 JSON 的接收入口，但该入口不提供逐包保护；新版手机始终使用确认方式。

## 调试日志和代码

手机 `[BLE TX]` 记录请求 ID、包序号、长度与确认，`[BLE RX]` 记录事件及原因码；开发板串口 `[BLE RX]` 记录包 ID、序号、长度及处理结果。**不打印原始 JSON、载荷或密码。**

复测正确密码配置、错误后更正、中文名称和断连重试。异常时保留手机及开发板两侧同一请求 ID 的日志，区分分包、JSON 解析和联网错误。
